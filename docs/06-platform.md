# 6. Platform crate

`crates/platform/` is the **only** crate with OS-specific code. It
implements the traits defined in `core` — `Engine` (server side),
`Injector` (client side), `Clipboard` — plus the input capture that
feeds the server.

## 6.1 Entry points

`crates/platform/src/lib.rs` dispatches per OS:

- **`server(display)` → `(Receiver<Message>, Box<dyn Engine>,
  Box<dyn Clipboard>, Arc<Liveness>)`** — start local input capture and
  build the engine + clipboard. The receiver is the channel of local
  input messages the server's main loop consumes.
- **`client(display)` → `(Box<dyn Injector>, Box<dyn Clipboard>)`** —
  the client's control of its own screen.
- **`raise_priority()`** — high priority (not realtime) so the
  millisecond-paced motion loops are never starved by busy apps.
- **`secure_desktop_active()`** — Windows: is the UAC secure desktop the
  current input desktop? (No process can inject into it.)
- **`primary_display()`** — the machine's real display geometry
  (physical pixels + DPI scale), used to build machine-accurate default
  layouts.
- **`hostname()`** — the OS host name.

`unsupported.rs` stubs every entry point so the crate compiles on any
OS and fails at runtime with a clear message on unsupported ones.

## 6.2 Key identity: USB HID usage ids

**File: `crates/platform/src/keys.rs`**

Keys travel over the wire as **USB HID usage ids**. Each backend
converts at its edge:

```
Linux X11:   keycode - 8 → evdev → HID      (capture)
             HID → evdev → keycode + 8      (injection)
Linux WL:    evdev → HID / HID → evdev      (future backend, same table)
Windows:     set-1 scancode (+E0 flag) → HID / HID → set-1 scancode
```

Because the wire format is OS-neutral, a Windows server driving a Linux
client delivers the *physical* key the user pressed; each machine's own
layout then produces the character.

- `hid_from_evdev` / `evdev_from_hid` — the Linux tables.
- `hid_from_scancode` / `scancode_from_hid` — the Windows set-1 table
  (with the E0-extended flag).
- A consistency test keeps the two directions in sync.
- `ESCAPE_KEY_HID = 0x47` — **Scroll Lock**, the escape key: while the
  cursor is on a client, Scroll Lock hands control back to this machine
  immediately (the classic KVM "unstick"). Intercepted only while away.

## 6.3 Linux / X11 backend

**Directory: `crates/platform/src/x11/`**

Three pieces, each with its own X connection so nothing contends:

- **`capture/`** — the capture thread reads **XI2 raw events** (motion
  deltas, buttons, keys) straight from the input devices and forwards
  them as protocol messages. Raw events are generated by the *hardware*,
  never by programmatic warps — so warping the local cursor can never
  feed phantom motion back into the session. The same thread executes
  every cursor *control* action (grab, warp, hide/show) because the
  client that grabs the pointer must be the one that warps it. A
  **beacon thread** on its own connection polls the real pointer
  position (a busy X server can delay its round-trips without stalling
  the cursor stream) and emits position beacons at ~6 ms cadence. Once
  the position has not changed for a few consecutive queries it backs
  off to 25 ms — nothing to report — and drops back to 6 ms the moment
  the pointer moves again. Crossing latency is untouched: crossings are
  driven by raw motion deltas and the *client's* beacons, never by this
  thread.
- **`engine.rs`** — `X11Engine` implements `core::server::Engine`;
  cursor control is delegated to the capture thread via
  `CaptureCommand`s (warp / grab / isolate / hide-show); every command
  also writes a byte to the capture loop's **wake pipe**, so an idle
  capture thread is woken out of `poll(2)` immediately — commands are
  never delayed by an event-driven wait.
- The capture loop itself is **event-driven**: it blocks in `poll(2)` on
  the X connection fd plus the wake pipe, and only wakes for a reason —
  an X event, an engine command, or a pending cadence duty (a beacon to
  send, a held key to repeat). Fully idle it sleeps in the kernel; while
  the cursor is on a client it wakes on a slow tick (100 ms) so the
  supervisor's heartbeat keeps advancing.
- **`injector.rs`** — `X11Injector` implements `core::client::Injector`:
  XTest fake input for relative motion/buttons/keys/wheel, XFixes for
  cursor hide/show, `X11Clipboard` (arboard) on its own lock.
- **`buttons.rs`** — X11 button ↔ canonical button id, and wheel
  translation (one notch per press pair, never doubled).

**Kernel device isolation** — `crates/platform/src/evdev/`:

While the cursor is on a client, apps that read *raw* events (browsers,
smooth-scroll terminals, TUIs) would still react to forwarded input —
no X grab can suppress raw delivery. The evdev reader therefore grabs
every physical pointer and keyboard at the kernel with `EVIOCGRAB`
while remote: X receives zero events (raw included) and the local
desktop literally sees nothing. It reads the devices directly and
forwards the same protocol messages (motion coalesced at the shared
cadence, wheel, buttons, keys, Scroll Lock escape). On return home the
grab is released and X capture resumes.

- `device.rs` — open/classify devices, translate kernel events.
- `reader.rs` — the reader thread: **event-driven** — it blocks in
  `poll(2)` on the device fds plus a wake pipe (transitions and fresh
  device lists write the pipe), so idle it sleeps in the kernel instead
  of busy-draining. It grabs/releases at the kernel on control
  transitions, and drains-and-discards while local so a boundary
  crossing never carries stale events across it.
- `hotplug.rs` — the enumerator thread: watches `/dev/input` with
  **inotify** and only re-opens the devices when something actually
  changed (hot-plug is signalled immediately); a 30 s fallback scan
  catches what inotify cannot see (permission changes). Device opens can
  block — they run on this thread, never on the reader's.
- The reader is **X-free by design** — a future Wayland backend reuses
  it unchanged.
- Reading `/dev/input` needs a one-time grant; the installer's udev rule
  provides it (see [Build & release](09-build-release.md#92-input-device-access)).

## 6.4 Windows backend

**Directory: `crates/platform/src/windows/`**

Mirrors the X11 backend structure exactly — same `Engine`/`Injector`
contracts, same canonical HID key model, same message flow:

- **`capture.rs`** — a hidden message-only window registered for **Raw
  Input** (`RIDEV_INPUTSINK`), forwarding hardware mouse deltas,
  buttons, wheel and key transitions on a background thread. Keyboard
  auto-repeat is deduplicated (raw input does not suppress it). A timer
  polls `GetCursorPos` every 8 ms and forwards *changed* positions as
  beacons (mirroring the X11 beacon thread). `SetCursorPos` never
  generates raw input, so the anti-oscillation design carries over
  unchanged.
- **`engine.rs`** — `Win32Engine` (server side): `SetCursorPos` warp,
  `ShowCursor` hide/show, clipboard.
- **`injector.rs`** — `Win32Injector` (client side): absolute
  `SetCursorPos` placement, `SendInput` injection in scan-code mode
  (layout-independent), `Win32Clipboard` (`CF_UNICODETEXT`).
- **`isolation.rs`** — the client's equivalent of the server's device
  grab: **low-level hooks** (`WH_MOUSE_LL` / `WH_KEYBOARD_LL`) swallow
  hardware-origin input while this machine is controlled remotely, and
  pass everything injected (`LLMHF_INJECTED` / `LLKHF_INJECTED` flags) —
  so the shared cursor and the user's own software work, but the
  laptop's touchpad cannot fight the injected stream. A watchdog
  releases local input if steering stalls (2 s), when the machine
  resumes from sleep, or when the UAC secure desktop appears — this
  machine is never left input-trapped. See also
  [`secure_desktop_active`] (§6.1).
- **`timer.rs`** — a 1 ms high-resolution timer: Windows' coarse default
  timer (~15 ms) would turn the millisecond-paced loops into clumps.
- `raise_priority` uses `HIGH_PRIORITY_CLASS`; the process is made
  per-monitor DPI aware so all coordinates are physical pixels.

## 6.5 Porting a new OS

Add a backend in three steps:

1. Implement `core::server::Engine` + `core::client::Injector` +
   `core::clipboard::Clipboard` for the OS (mirror the X11 or Windows
   module), plus the input source (capture) the server consumes.
2. Register it in `crates/platform/src/lib.rs` behind the matching
   `#[cfg(target_os = "...")]`.
3. Add the native key conversion into `platform::keys` (or reuse the
   existing tables — Wayland delivers evdev codes, so it reuses the
   Linux table unchanged).

macOS is not implemented; the stubs in `unsupported.rs` keep the whole
workspace building everywhere.
